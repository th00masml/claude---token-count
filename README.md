# t2sbench: small LLMs, prompting strategies and LoRA for text-to-SQL

Reproducible benchmark that compares small language models (up to 24B parameters), SQL
generation strategies (S0-S5) and LoRA fine-tuning on two test sets: a 150-question
stratified sample of BIRD dev (with and without `evidence`) and a synthetic shop-floor
database with legacy table names and single-letter status codes, which simulates the
production system the tool is eventually meant for.

Data boundary: only public data (BIRD) and synthetic data generated by this repo. No
company data goes into this repo or onto the benchmark machine.

## Setup

```bash
uv sync                      # Python 3.11, core deps
uv sync --extra train        # + QLoRA training deps (stage 6, needs the GPU box)
uv run pytest -q
```

## Commands

```bash
uv run t2sbench build-synthetic          # DB + test/train/val questions into data/synthetic/
uv run t2sbench fetch-bird dev           # public BIRD dev into data/bird/ (not committed)
uv run t2sbench fetch-bird train         # BIRD train, only for LoRA L1 (stage 6)
uv run t2sbench sample-bird              # stratified 150-question sample, seed 42
uv run t2sbench discover-models          # which configured models really exist -> results/model_availability.json
uv run t2sbench check-sql DB "SELECT ..."
```

## Layout

```
config/models.yaml        candidate models, Bedrock region, vLLM settings (precision, max-model-len)
config/prices.yaml        token prices (null = unknown, never guessed) and the 50 USD budget
src/t2sbench/
  datasets/bird.py        download, stratified sample, train/dev disjointness check
  datasets/synthetic/     generator.py, templates.py, build.py, schema_doc.yaml, codes.yaml
  models/                 base.py (generate / generate_with_tools), cache.py, discovery.py
  strategies/base.py      Strategy interface (S0-S5 come in stages 2 and 4)
  validator.py            sqlglot: one statement, SELECT/WITH only, no DDL/DML/PRAGMA/ATTACH
  executor.py             SQLite mode=ro + PRAGMA query_only=ON, 10 s timeout, 1000-row cap
  evaluate.py             execution accuracy, bootstrap CI, McNemar
  run.py                  typer CLI
data/synthetic/*.jsonl    committed question sets (the .sqlite is rebuilt deterministically)
notebooks/                one notebook per stage with the results shown to the reviewer
tests/                    pytest
```

## Synthetic database

14 tables (`LIN`, `MCH`, `MCH_STAT`, `ZMIANA`, `PRZYCZ`, `PRZEST`, `PROD`, `ZLEC`,
`ZLEC_POZ`, `OPER`, `OPER_ZM`, `PROD_REJ`, `BR_TYP`, `BRAKI`), about 16k rows covering
2026-01-01 to 2026-03-31, seed 42. `codes.yaml` is the source of truth for code values:
the generator draws from it and a test fails if the DB holds an undocumented code.

Questions come from intent templates. 10 test templates give 4 instances each, rendered
in Polish and English with the same gold SQL (80 records, 40 pairs). 20 different train
templates give 440 single-language instances, split into 400 train (200 PL + 200 EN) and
40 validation (20 + 20). Tests check that every gold query runs and returns a non-empty,
non-NULL result, that no test template, SQL skeleton (literals masked) or question text
appears in the train/val pool, and that ORDER BY ... LIMIT gold answers have no ties at
the cut-off.

## Evaluation rules

Execution accuracy compares predicted and gold results as a multiset of tuples, numbers
rounded to 4 decimals, order ignored unless the gold SQL has a top-level ORDER BY. Column
order matters, column names do not. Every query, including exploration queries in S3 and
SQRL, goes through the validator and the read-only executor.
